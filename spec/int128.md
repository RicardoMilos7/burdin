# 128-bit integers

Issue #273. `i128` and `u128` are the two 128-bit integer types. This page is the behavior the compiler implements and
the tests that witness it. `tests/int128/` holds the conformance programs, and `tests/check_bindgen.py` holds the two
checks that run outside the conformance suite. The stage 0 and stage 1 pages listed both types as "when wanted".

Every rule below is witnessed by the tests named in it. A rule without a witness is not a rule.

## I128-1. Types and representation

`i128` and `u128` are 16 bytes with 16-byte alignment, the LLVM `i128` type. A container's allocator request is capped at
8 bytes of alignment today (`allocators.md`, AL2; #917). A `repr(C)` struct that holds one follows
the C layout: the field is placed at its own alignment, and the struct's size is padded to its alignment. Inside the
compiler, every integer value is carried as an `i128`. A `u128` value above `i128::MAX` is carried as its two's
complement bit pattern, so it is negative in the carrier and is read back as unsigned wherever its type is known.
Ordering of `u128` values uses the order key of the type (the value with its top bit flipped), which is order-preserving
for the whole type.

Witnesses: `tests/int128/layout.bd` (sizes and alignments, including `repr(C)`), `tests/int128/literals.bd`,
`tests/int128/comptime_ranges.bd`.

## I128-2. Literals

An integer literal must fit its type. A literal that does not fit is E0008 at the literal. `i128` accepts `-2^127`
written with a minus sign. `u128` accepts every value up to `2^128 - 1`. A literal above `u128::MAX` is read by the
lexer, which reports E0008 there; a file with a syntax error is not type checked (`spec/check.md`, CK4), so that file
has no other diagnostics. Negating an unsigned value is a type error, E0003, as it is for `u64`.

Witnesses: `tests/int128/literal_out_of_range.bd` (one past `i128::MAX`, one below `i128::MIN`, `-1` for `u128`),
`tests/int128/literal_too_large.bd` (the lexer case), `tests/int128/literals.bd` (both ends of each range).

## I128-3. Division and remainder

`/` and `%` truncate toward zero, as they do for the other integer types. Division by zero panics in every profile with
`division by zero`. `MIN / -1` has no 128-bit result: a debug build panics with `attempt to divide with overflow`, and a
release build wraps, giving `MIN` for the quotient and `0` for `MIN % -1` (`spec/profiles.md`).

The 128-bit quotient and remainder come from a routine in the generated runtime, not from a compiler runtime library.
MSVC has no `__divti3`/`__udivti3`, so the compiler does not rely on one. A divisor below `2^64` takes a short path; a
larger divisor takes the long-division path.

Witnesses: `tests/int128/division.bd` (truncation, a divisor above `2^64`, Euclidean helpers),
`tests/int128/divide_by_zero_aborts.bd`, `tests/int128/divide_overflow_aborts.bd` (debug only),
`tests/int128/divide_min_neg_one_release.bd` (release only).

## I128-4. Arithmetic, overflow, and shifts

`+`, `-`, `*`, and unary `-` panic in a debug build with `attempt to add with overflow`, `attempt to subtract with
overflow`, `attempt to multiply with overflow`, or `attempt to negate with overflow`, and wrap in a release build. The
`wrapping_`, `checked_`, `saturating_`, and `overflowing_` method families exist for both types with the same meanings as
for the narrower types.

A shift by the bit width (128) or more panics in every profile with `attempt to shift with overflow`. A right shift of a
negative `i128` is arithmetic: it keeps the sign.

Witnesses: `tests/int128/add_overflow_aborts.bd`, `tests/int128/subtract_overflow_aborts.bd`,
`tests/int128/mul_overflow_aborts.bd`, `tests/int128/negate_overflow_aborts.bd` (all four debug only),
`tests/int128/shift_aborts.bd`, `tests/int128/shifts.bd`, `tests/int128/ops_and_casts.bd` (the method families).

## I128-5. Formatting

`to_string()` and `{}` print the decimal value, with a `-` for a negative `i128`. `{:?}` on a struct prints the field
values with the same decimal form. `{:x}`, `{:#x}`, and `{:b}` format the bit pattern as unsigned, and a width (`{:>45}`)
pads the value. `to_string_radix` writes lowercase digits with a leading `-` for a negative number. The decimal and
radix routines are written in the standard library (`std/src/fmt.bd`, `__fmt_i128`, `__fmt_u128`).

Witnesses: `tests/int128/literals.bd` (`{:x}`, `{}`), `tests/int128/ops_and_casts.bd` (width, `{:#x}`, `{:b}`,
`to_string_radix`, `{:?}` of a struct).

## I128-6. Parsing

`i128.parse(s)` and `u128.parse(s)` accept exactly the decimal strings whose value is in the type's range. A string
above the range, a negative value for `u128`, an empty string, and a string with a non-digit are errors. The parser is
written in the standard library, in base 10 (`std/src/int.bd`).

Witnesses: `tests/int128/parse.bd`.

## I128-7. Casts

`as` between `i128`/`u128` and the other integer types keeps the low bits when narrowing. When widening, a signed source
is sign-extended and an unsigned source is zero-extended. `as` from a float saturates: a value above the type's range
becomes the maximum, a value below becomes the minimum, and a negative float cast to `u128` becomes `0`.

Witnesses: `tests/int128/ops_and_casts.bd` (`i8 -1` to `u128` and `i128`, `u128` to `i64`, saturating float casts),
`tests/int128/literals.bd` (`i128` to `u64`, and `u128` shifted down to `u64`).

## I128-8. Ordering and ranges

Comparison, `min`, `max`, and sorting follow the numeric order of the type, so `u128` values above `i128::MAX` sort
after the smaller ones. A `for` loop over a range of a 128-bit type, and a range iterator, run in order across the
whole span, both at compile time (`comptime` blocks and `const`s) and at run time. The bounds are compared in the
type's order, and the counter does not overflow at the top of the type: an inclusive range ending at `u128::MAX` stops
there.

Witnesses: `tests/int128/comptime_ranges.bd` (a compile-time range straddling `2^127`, a `for` over a range variable, a
range iterator, and a `comptime` shift), `tests/int128/runtime_ranges.bd` (the same at run time, including ranges that
end at `u128::MAX`), `tests/int128/ops_and_casts.bd` (comparisons, `max`/`min`, and `sort`).

## I128-9. The C boundary

A 128-bit integer cannot be a parameter or a return type of an `extern "C"` function, because C has no 128-bit integer
type that every platform declares. The compiler reports E0162 and suggests passing the value through `CPtr<i128>`.

Witnesses: `tests/int128/ffi_reject.bd`.

## I128-10. Patterns and exhaustiveness

Integer patterns and ranges cover the whole 128-bit span, including a negative lower bound equal to the minimum
(`-170141183460469231731687303715884105728..=-1`). Exhaustiveness is checked over the full range of the type: a `match`
on a `u128` that stops below `2^128 - 1` is E0006, and so is an `i128` match with no arm for the positive values.

Witnesses: `tests/int128/patterns_nonexhaustive.bd` (E0006 for both types), `tests/int128/ops_and_casts.bd` (`classify`
and `sign`, exhaustive over the full range).

## I128-11. Hashing, equality, derived traits, and collections

`Hash` mixes both 64-bit halves of the value, so values that differ only in the high half hash differently. `Eq`,
`Ord`, and `Hash` derive over 128-bit fields. `List`, `Map`, and `Set` hold 128-bit values with the same behavior as for
the narrower types.

Witnesses: `tests/int128/ops_and_casts.bd` (a derived `Ord` and `Hash` struct with 128-bit fields, `List<u128>` sorted,
`Map<u128, i32>`, `Set<i128>`). The high-half hashing is not observable from a program's output and has no direct test.

## I128-12. Not covered

This change does not cover these, and no test claims them:

- Serialization (`spec/serialization.md`) of a 128-bit value. The data model has no 128-bit integer yet.
- `[rust.crates]` interop with Rust's `i128` and `u128`. No interop test uses them.
- `--sanitize` (`spec/sanitizers.md`) on 128-bit operations. No sanitizer test exercises them.
- Float formatting of a value converted from a 128-bit integer, which is the existing float format.

## I128-13. C headers

A 128-bit integer has no C spelling, so neither the export header nor a generated binding can name one.
`burdin bindgen --export` reports a `repr(C)` struct with a 128-bit field as E0263 and writes no header. `burdin bindgen`
skips a C function that uses C's `__int128` and says so in the module, and generates the other functions.

Witnesses: `tests/bindgen/export_wide/` through `tests/check_bindgen.py` (the export report and the missing header), and
`tests/bindgen/headers/wide.h` through `tests/check_bindgen.py` (the skipped function and the generated one).
